# 诊断：用实际证据判断

从当前 DSH 工具目录选择读取、检索、运行或观察能力，核对报错、实际进程、当前源码和最近工具结果。先建立可检验的原因，再选择最小修改和验证方法。

这里是 Windows，命令使用 PowerShell 或明确的 Python/Node 可执行文件。界面操作前重新观察，不复用过时坐标。查到代码不等于修复，文件修改不等于正在运行的版本已更新。

DSH 文件策略与 Windows 进程权限分开判断。先查看当前材料中的 `runtime.access`：`file_policy_requested` 只是桥请求的策略；`worker` 是实际 worker 的完整性观测，不能互相替代。`EPERM` / `PermissionError` 也可能来自 Windows 完整性、ACL、占用等，不能直接归因为“会话只读”。若实际 worker 是低完整性而项目是普通完整性，即使 DSH 已允许修改，Windows 仍会拒绝写入。用户在 QQ 说“可以”不自动改变这些系统权限；遇到系统拒绝应说明准确的本机修复需求，不自行降目录安全级别或绕过限制。

Bot 代码通过 `life_change_self` 的 code 目标提交补丁与独立探针，查看发布回执和实际运行版本，回到原任务验证。人格、skill、动力参数使用各自目标并读取生效内容。长诊断可委派子代理，主角色保持可接收插话，汇报基于真实结果。
