## 一、做了什么（按主题）

### 1. dsh 错误可发现性（P46 / P48 / P52 / P56）

**问题**：dsh 失败时只给一句「inspect runtime availability and model settings」，
谁也查不出根因。当天 completed=2 / failed=9。

**改成**：
- 真实原因在 `RunResult.events` 的 `turn/end` 里，原来被 `raise RuntimeError('did not complete')` 丢掉了。
  新增 `_turn_error()` 按优先级挖出来。
- `classify_failure()` 六类分类：adapter 未注册 / 鉴权失败 / 需要原生 Anthropic 端点 / 模型名不存在 / 超时 / 连不上。
- 去掉误导性的 `DEEPSEEK_BASE_URL` 注入（adapter 只读 `DEEPSEEK_API_KEY`，注入一个没人读的变量比不注入更糟）。
- **后又按用户原则去掉处方**：不再说「得换回官方 provider」这种建议，
  只陈述事实（401 + 底层原文 + 当前配置 + adapter 名）并给出查证路径（`--dump-config`）。

**怎么验的**：真跑 dsh，对比改前改后输出；`classify_failure` 五类输入自测；部署后重启再跑一次。

### 2. dsh 假成功（P56，最严重的一次）

**问题**：某次真跑 dsh 返回 `status=completed / return_code=0 / seconds=0.066 / output=''`，
而会话目录**一个文件都没有**。0.066 秒不可能调用模型。

**根因**：**是我自己的补丁把 worker 文件截断了**——`src[:idx] + new_block` 把
`classify_failure` 之后的所有内容（含 `_turn_error()` 和整个 `if __name__ == '__main__':`）全删了。
`grep -c "__main__"` 结果为 0。

**改成**：
- 从 git 取回被删的两段，保留新版 `classify_failure`
- **三层判据**：退出码 0 + 输出非空 + 会话目录真有新文件，三条都满足才算 completed
- 失败文案带秒数：「0.066 秒就返回…这说明它根本没启动——不是做完了一件事，是没做任何事」

**怎么验的**：四种输入的逻辑判据全 PASS；真跑验证 `status=failed / seconds=1.963 / 真实 traceback`。
**历史核查**：`kind=dsh` 全库 11 条中 completed 2 条，seconds 分别是 665.6 / 612.0，都有完整输出——
**所以历史成功率没有被假成功污染。**

### 3. 截断丢失行动（P50 / P50b / P51）

**问题**：`truncated=True` 时整轮降级成纯回复，actions 全丢。
她自己发的「这就去查」永远落不了地，一天内同样形态出现两遍（21:55、22:05）。

**根因链**（四次实测全部一致）：
```
项目状态校验失败 → 她改成 active（改对了）→ 输出撞上限被截断 → actions 全作废
```

**改成**：
- **P51**：截断但 JSON 结构完整时恢复 actions。三条判据从严：
  ① 整体 `json.loads` 成功（不是正则抠）② 每个 action 单独过 schema，任一不过整批丢
  ③ 恢复后告诉她「截断不等于失败」
- **P50**：结构残缺时也不静默——把「上一轮有 N 个行动被打断」作为事实摆到下一轮 state
- **P50b**：这条事实的消费时机改成**请求成功之后**，避免「消息没到但事实已被消费」

**怎么验的**：八项判据（含三个反向：半截 JSON 必须丢、action 缺必填整批丢、无 actions 不恢复）；消费时机四场景。

### 4. 失败记录没有入口（P52 / P53）

**问题**：120 条 error 记录写在库里、`reason` 写得很细（p50=52 字符），
但 `memory op=search` **只查 `companion_actions`，从不查 `companion_activity`**——
她在工具层面完全读不到。**不是没记，是没给入口。**

**改成**：
- **A**：`memory op=search` 支持 `scope='errors'`，默认不搜（否则正常检索被噪音污染）
- **B**：awareness 增加 `failures` 汇总段：条数、按原因分类、怎么查的指引；
  刻意不说「这很严重」，也刻意在数量为 0 时明说「没有失败记录，这是事实」
- **P53**：`本轮状态未能保存` 那条路径以前不传 details，补齐 reason + 出错位置

**怎么验的**：生产实测 B 返回 120 条 / 分组 / how_to_look；A 查到具体条目；
**反向判据**：默认 search 来源集合 `{'action_record'}`，未被污染。

### 5. 记录自相矛盾（P55）

**问题**：同一条子 agent 记录里：
```
summary   "已完成…没有未完成事项"    ← 子 agent 自述
outcome   "incomplete"              ← 系统判定
remaining ["命令行输出的那行文字"]   ← 就在 summary 下面，直接打架
```

**改成**：标注来源，并列不合并——
`子 agent 自己的说法（不是系统判定）：…` / `系统判定的结果 incomplete（任务跑完了，但验收判据没达成）`
**没删 summary、没改内容、没替她选哪个算数。**

**怎么验的**：生产真实记录渲染，四条判据全 PASS。

### 6. verification 永远 pending（P49 + 回填）

**问题**：`_verify` 没有检查项时返回 `None` → 永远 pending。
而 `VERIFICATIONS` 里早就定义了 `unverified`，只是从没返回过。

**改成**：终态 + 无检查项 → `unverified`；运行中 + 无检查项 → `None`。
**并按用户原则改文案**：不说「待验证」（那是承诺），说「没有可核验的证据」（这是事实）。

**怎么验的**：7 个用例（终态四种 / 运行中两种 / 有检查项两种）全 PASS；
**带审计回填 5 条**，每行写一条「这行为什么验不了」；幂等验证第二次 0 条。

### 7. 28/289 条 `details={}`（P53 + 回填）

**改成**：状态保存失败路径补 `reason` + traceback 位置（实测 `reason: "模拟… @boom:36"`）；
**历史 289 条**带审计回填，写「这条记录写于修复之前，失败原因当时没有记录（异常对象已不存在）」。
**不编造，但明确陈述「当时没记」这个事实。**

### 8. 示例写法照做会失败（P57）

**问题**：`AGENT_INSTRUCTIONS` 写 `inspect{agent_id}`，照字面执行必然 `agent_id_required`。

**判据更换过程**：先用「构造 action 过 schema」——**24 条全绿**。
**但那个绿是假的**：schema 只校验 `op` 在枚举、`arguments` 是字符串，
**不校验参数有没有放进 `arguments`**。换成可执行性判据才验出来。

**改成**：六个操作全部改成 `op` + `arguments({"agent_id":"…"})`，与 GUIDES 其他工具统一。

### 9. 后台任务无法枚举（P58）

**改成**：`op=list`，返回 job_id / 状态 / 启动时间 / 时长 / 日志路径；
状态判定**复用 `status()` 的同一套逻辑**（`_alive` + `_exit_code`），不另写一套；
`gone` 单独提示「不知道成没成功，不是成功也不是失败」。
