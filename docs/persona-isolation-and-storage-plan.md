结论：主要增长点是完整运行日志，其次是状态记录，当前并非长期记忆条目太多。仅 checkpoint 最多解决 WAL 部分；主库空闲页很少，单纯 VACUUM 的收益有限。

## 建议的存储优化顺序

### 先降低重复写入

对体积最大的请求描述、消息流和大型工具结果测量字段重复率，采用按内容 hash 去重或压缩存储，保留版本和可恢复的读取适配。工具产生的大文件放到人物资源目录，数据库保存受权限约束的引用。

不能直接跳过 `AgentSessions.apply_event` 中某种事件：当前实现要求 seq 连续，重放、使用量、来源追踪和恢复代码会读取事件内容。即使保存精简投影，也必须保留原始摘要、事件位置和所有消费者必需字段，并升级读写协议。

### 为运行日志建立分级保留

将个人长期记忆与运行诊断日志分开管理。先以可配置策略试行：最近 3 天保留完整诊断正文；更早且已经结算的退役会话归档压缩；热库保留定位、hash、类型、游标、必要回执与来源引用。

3 天是建议起点，不是已经启用的规则。任何活跃会话、未处理输入、未知操作、未核对发送、未完成任务、未投影用量和仍被引用的来源，都不按年龄强制删除。历史读取需要能够通过引用读取归档，不允许归档后静默召回失败。

归档仍属于原人物，遵守她的访问边界、遗忘与删除语义。不能把旧日志移入公共档案，让其他人物可以读取。

### 状态日志采用检查点与增量

`state_journal` 当前含完整 before/after 状态，是第二大占用项。先验证现有回放与遗忘重建依赖，再设计周期检查点和可重放增量。不能直接删除早期状态行，否则可能破坏关系、情绪和删除来源后的重建。

### 最后回收文件空间

先使用 SQLite 一致性备份，再在人物停止且没有连接持有库文件时执行已经验证的归档迁移。校验恢复、召回、幂等和来源之后，再做 WAL checkpoint 与数据库空间回收。

不能在运行中手动删除 `-wal` 文件，也不能用清空 `events` 或 `memories` 的办法压体积。

每个人物独立计算主库、WAL、归档和媒体大小；全局再计算总量。超过阈值时触发归档或报告，不能静默遗忘。分库解决身份隔离，不会自动降低总存储量。
