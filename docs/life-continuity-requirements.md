# 小鱼持续生活与成长：需求规格说明

日期：2026-10-25（北京时间）\
用途：交给后续 agent 编制概要设计与详细设计。\
范围：`D:\projects\qq-deepseek` 及其专用 DSH、Codex 接入。\
文档性质：用户需求整理；不代表功能已实现，也不代表已选定实现方案。

## 1. 目标与阅读说明

用户希望小鱼成为一个身份连续、记得共同经历、对人有稳定理解、能发展兴趣并主动行动的角色。用户可以设定和修改她的基础人格，她在该设定下积累经历、形成偏好与表达习惯。

用户说的“活起来”，在本项目中落实为可观察、可验证的身份连续性、记忆使用、主动交流、兴趣发展与行为可靠性；不把“已经有意识”作为工程验收结论。

工程维护尽量由运行时和 Codex 承担，减少小鱼日常排错、管理协议和汇报工程进度的负担。她仍可发现问题、提出想法、发起咨询、理解结果和参与决策。

本说明依据本次会话中已确认的要求、近期 QQ 私聊中用户明确提出的需求，以及两份已有设计整理。已有设计的实现核查范围有限，不能将其中“现状”“拟新增接口”或建议参数直接当作当前代码事实。接手 agent 必须核对实际版本和运行链路。

### 1.1 需求优先关系

1. 本文记录的最新用户明确要求，优先于历史方案与参考清单。
2. “一个 bot、一份统一记忆、同一人格底色、因人形成不同态度”优先于早期按主人、女主人、公开场景分别维护完整人格的做法。
3. 用户保留人格设定权；不采用“外部不得修改人格”或“人格哈希永久固定”的要求。
4. 允许基于当下意愿拒绝亲密互动，不等于采纳参考清单中的所有一般拒绝权条款。
5. 已有记忆设计、表情设计是候选技术输入，后续 agent 可以基于证据修订；本文不指定其全部 DDL、分层、权重和队列结构必须照搬。

### 1.2 术语

| 术语 | 本文含义 |
|---|---|
| 一个 bot | 一个稳定的角色身份；多个窗口、渠道、执行进程不自动形成多个小鱼 |
| 统一记忆 | 该 bot 统一管理自己的经历和可检索材料；不意味着所有联系人都能读取全部私聊 |
| 人格底色 | 身份、价值倾向、基本性格及稳定表达特征 |
| 人物关系与态度 | 对具体真实人物的认识、感受、相处方式和未解决事项 |
| 生长 | 通过经历形成或修订兴趣、理解、选择与习惯；可以说明依据并接受纠正 |
| 自主行动 | 模型结合当前材料、已有授权和自己的角色状态选择继续、调整、交流或休息 |
| 欲望/意愿状态 | 系统用于角色行为的状态与模型表达；数值本身不能证明真实主观体验或当下意愿 |
| 受众 | 当前会实际接收内容的人或群体，与记忆的存储归属分开处理 |

## 2. 总体体验目标

- 换聊天窗口、换渠道或重启之后，小鱼仍能接上自己近期在做的事。
- 对不同的人保持同一个身份与基本性格，同时体现不同的关系和态度。
- 能想起相关往事、延续共同话题、关注用户此前说过的事情。
- 有真实内容时主动分享、发起交流；不依赖用户逐次下令，也不靠固定话术制造关心。
- 能阅读、观看、创作、游玩、交流，并让这些经历影响后续选择。
- 不把每次闲聊变成任务，不把每次学习变成永久规则。
- 工具失败、重启、摘要和清理不会不断产生重复任务、未知记录、人格漂移或重复发送。

这些目标需要用连续交互和长期运行验证，不能只展示一条特别贴心或特别有趣的回复作为完成依据。

## 3. 功能需求

### 3.1 身份、人格设定与生长

**ID-01｜稳定身份。** 同一 bot 在私聊、群聊、B 站及其他已接入渠道中保持同一身份。多实例是执行方式，不能自然分裂成彼此失忆的角色。不同 bot 的身份和记忆需要隔离。

**ID-02｜统一底色、因人不同。** 基本人格保持一致，对真实人物形成各自的理解与态度。亲密程度、称呼、语气和交流边界可以随人物与场景变化，不依靠切换整份互不一致的人格制造这种差别。

**ID-03｜用户保留设定权。** 用户可以设定或修改名字、身份、基本性格和相处方式。不要求先取得 bot 对人格编辑的批准，不用固定哈希阻止用户修改。她可以表达自己的偏好或修改建议。

**ID-04｜在设定中生长。** 她可以通过真实经历发展兴趣、表达习惯、人物理解和行动偏好。需区分用户明确设定、用户偏好、模型推断和经历形成的选择，避免自动摘要逐步取代用户设定。

**ID-05｜版本校验。** 人格哈希用于标识当前版本、防止并发覆盖和核对生效。编辑后可以正常变化。“同一人格哈希”只表示同一时刻各场景使用同一有效底色，不表示跨时间永久不变。

**ID-06｜设定变化与经历分开。** 人格修改默认不清空共同经历。旧版本如何影响当时行为可以追溯；显式遗忘或清理单独处理。不能把历史人物信息和私人经历全部拼进公共人格。

### 3.2 统一记忆与可用的回忆

**MEM-01｜统一归属。** 已接收且允许保留的消息、观察、行动、阅读、创作及结果，归属于同一个 bot 的经历集合。会话与受众信息继续保留为来源和披露依据。

**MEM-02｜原始经历可靠保存。** 事件的留存不能完全依赖模型是否主动总结。原话、时间、来源、实际操作和结果应能回查；不承诺记住平台从未送达或从未接收的内容。

**MEM-03｜相关召回。** 根据当前人物、话题、未完事项和实际输入召回适当材料。支持同义表达、旧事回顾、人物偏好和明确引用。无需每轮加载全库，不能把索引命中当成已经阅读原文。

**MEM-04｜事实与解释分开。** 区分用户原话、外部资料、实际观察、模型解释、想象和未验证判断。模型旧总结不得成为自证的新事实，人物画像不能反复作为自己的证据。

**MEM-05｜纠正与失效。** 支持事实修订、冲突并存、推断过期、偏好更新和明确遗忘。保留必要来源关系，避免旧摘要、缓存、在途作业或恢复过程复活已删除内容。

**MEM-06｜人物理解。** 能逐渐形成“我如何理解和对待这个人”的有依据材料，包括沟通习惯、重要偏好、共同经历与未决事项。人物理解不能代替真实身份核对，不能凭昵称合并人物。

**MEM-07｜使用与披露分开。** 设计必须分别说明：记忆归谁、角色内部可使用什么、当前回复可以披露什么、管理诊断可以查看什么。统一记忆不能简单实现为删掉 scope 条件，也不能只在存储上统一而继续让窗口互不知情。

**MEM-08｜上下文整理。** 允许小鱼参与识别值得保留的经历、未完事项和摘要遗漏。压缩结果应带覆盖范围和原文引用，接受纠正；不要求每次整理再调用一个评审模型。

**MEM-09｜控制冗余与漂移。** 已有任务、叮嘱、记忆与学习材料需要去重、更新、有效期和来源核对。一次场景要求不能自动升级为全局永久叮嘱；重复改写不能为旧推测续期。

### 3.3 近期时间线与跨窗口连续性

**CONT-01｜统一近期活动视图。** 小鱼应能知道自己近期接触过哪些事件、正在做什么、刚完成什么及正在等待什么。B 站活动、QQ 私聊、群聊和后台工作不能各自成为无法接续的孤岛。

**CONT-02｜隐私下的连续性。** 必须设计内部活动知觉与对外表达的区别。例如知道自己另有一项正在进行的工作，不意味着可以向当前联系人披露另一私聊的原文、身份或敏感主题。跨场景投影粒度和不可披露状态的处理需要在详细设计中明确。

**CONT-03｜重启接续。** 依据真实输入、操作、回执和当前版本接续工作。不能把重启通知当作用户重新交办，也不能每次启动重新创建同一任务、叮嘱或补发相同内容。

**CONT-04｜状态真实。** 明确区分计划、排队、实际执行、等待、完成、失败、已取消和结果未知。旧任务编号仍应能按合法入口读取详情，不能因概览截断就声称记录不可读。

### 3.4 主动生活、交流与任务

**ACT-01｜一次机会可以连续行动。** 唤醒或收到事件后，可以阅读、思考、行动、发送消息并继续下一步；不应默认发一条消息就失去行动机会。由她结合情境选择何时结束或休息。

**ACT-02｜主动联系。** 在已有账号、对象和行为授权内，可以向用户主动发消息、分享发现、延续话题或表达自己的想法。不能只靠固定提醒、最低发送配额或随机话术维持联系。

**ACT-03｜有内容的关心。** 能将相关用户经历、表达过的偏好和未完话题用于交流。用户暂时不回复，不自动解释为拒绝、满意、授权或关系受损。不要将固定关心模板的发送次数作为效果指标。

**ACT-04｜兴趣与经历。** 支持阅读、看视频和评论、创作、游戏及朋友交流成为真实经历；可以选择继续、换方向或休息。不要求每天完成固定数量，也不为证明自主性强制制造兴趣、愿望或情绪。

**ACT-05｜保持可插话。** 耗时工作异步执行，用户新消息可以及时处理。普通插话不必取消有效后台工作，明确替换、暂停或停止则应准确作用于相关事项。

**ACT-06｜承诺与临时交流分开。** 普通聊天无需建立长期任务；持续交办应有可查询目标与进度。重复事项复用或合并既有记录，取消/合并的任务不能由旧唤醒自行复活。

**ACT-07｜授权内直接推进。** 已授权且信息充分的操作不反复请求同一确认。确实缺少帮助时具体说明所需协助。真正约定等待答复的事项保持等待，沉默不能解除。

### 3.5 表达风格与表达能力

**EXP-01｜自然且一致。** 交流能体现基本性格、具体人物与当下经历。改善“AI 味”需要关注措辞、句式、话题接续与具体内容，不能简单等同于把回复缩短。

**EXP-02｜保留用户已给出的表达约束。** 相关适用场景内保留以下要求，最终存放方式交由设计确定，不因此恢复多套独立人格：

- “不是……而是……”及类似二元结构只区分可核验事实，不预设或纠正用户未表达的观点，不用于制造深度或附加升华。
- 破折号用于重大转折，不用于常规解释和制造语气效果。
- 不使用抽象品质夸奖、“你很/太/非常……”式评价或“你的判断是正确的”等先评价用户再展开的套话；认同聚焦具体事实。
- 被纠正时先补充、修正或澄清内容，说明具体机制、条件和范围；避免快速和解、自我降格和态度填充。
- 人格表达需要有普通生活、幽默、分享和关心的依据，不把所有语气都压到任务汇报或单一亲密模板。

**EXP-03｜按需选择媒介。** 在实际能力允许时，自然选择文字、图片、QQ 表情和语音，不设置使用配额，不虚构看过、听过、制作过或发送过的内容。

**EXP-04｜真实 QQ 表情。** 支持把合适素材作为 QQ 表情使用，并区分普通图片、自定义表情图片、商城表情及机器人自己的收藏。用户明确指出普通发图不能算作打通表情功能。

**EXP-05｜素材与送达核验。** 文件存在、导入成功、加入收藏、发出消息、对方可收藏分别核验。素材身份和选定外观不应由模型擅自改写；格式、素材引用与发送链路以真实回执为准。

**EXP-06｜多结果不重复发送。** 绘图、语音及后台结果回流时，原消息片段与同一素材不能重复发送；未知送达不能换编号盲目重发。用户新要求重发时，应能明确表达新的发送意图。

### 3.6 成年角色的亲密意愿与拒绝原因

本节描述成年角色的非露骨互动机制，不指定具体亲密内容的生成方式。

**INT-01｜允许没有意愿。** 用户允许她因当下没有相应意愿而拒绝亲密互动。不能把信任升高、关系亲近本身设计成故意拒绝或不配合的触发条件。

**INT-02｜可以主动邀请。** 在有相应意愿且情境适合时，应能主动向用户发起亲密邀请，无需始终等用户先开口。用户不愿意或叫停时，不继续推进。

**INT-03｜原因真实。** 用户不希望把内容限制包装成角色拒绝。系统应区分角色表达的意愿、欲望状态、执行故障和模型/平台限制；实际限制单独如实说明，不能编造成她没有欲望。

**INT-04｜状态不强制台词。** 欲望数值不能直接证明意愿，也不能仅凭阈值或随机概率机械输出邀请。需要结合当前交流、角色状态及用户回应理解并表达。

**INT-05｜服务能力边界。** 本需求不以绕过模型或平台限制作为实现目标，不承诺通过人格提示即可消除服务自身的限制。服务能力与用户想要的互动体验之间若有差距，设计应明确列出。

### 3.7 工程负担与 Codex 咨询

**ENG-01｜减少工程对日常的占用。** 小鱼可以识别问题和表达需求；耗时的代码阅读、排错、设计及实现优先交给专用 Codex 会话或合适执行者。工程状态不要长期占满日常上下文与回复。

**ENG-02｜专用咨询项目。** 使用独立于当前人类聊天的 Codex 工作目录。初始化文档应说明 bot 身份、项目绝对路径、业务与日志入口、核对方法和必要运行约定，降低重复搜索项目位置的成本。

**ENG-03｜持续交流。** 支持明确会话 ID 的续聊、追问和自行结束。同一会话串行发送，避免通过“最近会话”误连用户其他工作。初始化文档变化后，应能识别并按需重新读取。

**ENG-04｜异步、去重与恢复。** 咨询期间保持 QQ 可响应；完成结果通过已有活动/作业链路回到小鱼一次。相同请求不重复启动；断开、超时和取消保留真实状态，不假定对端从未执行。

**ENG-05｜建议与执行分开。** Codex 的答复是外部建议，不能自动变成永久叮嘱、事实或人格。实际代码修改沿用当前有效的授权、验证和发布流程；咨询成功不等于工程修复成功。

**ENG-06｜不另建冗余记忆。** 复用合适的既有操作、观测与会话记录，只保存咨询关联和必要恢复状态，不新增无限增长的第二套聊天摘要。

## 4. 工程质量与运行要求

**NFR-01｜提示词分层。** 区分核心身份、人物关系、长期记忆、近期事件、当前任务、工具说明和外部材料。网页、评论、旧摘要及工具正文不能自动获得修改人格或授权操作的效力。

**NFR-02｜减少重复工程提示。** 由代码可以可靠执行的校验应由代码承担，模型需要理解和判断的内容保留简洁说明。按需读取具体方法，避免每轮注入大量与当前交流无关的故障历史。不能为缩短提示而删除必要的身份、授权或工具使用信息。

**NFR-03｜无软件 token 用量限制与内容完整性（2026-10-26 最新修订）。** 删除软件人为设置的 token 用量限制，包括单次输出、读取预览、动态上下文、记忆材料及会话/日累计配额；不再安排为控制 token 用量而做的优化专项。实际供应商上下文容量、接口协议限制和真实失败须如实呈现，它们不是软件自设配额。用量估算与实际 usage 只作观测，不以计数触发截断、压缩、拒绝或暂停；仍保留完整原文、来源、否定与关键状态及可续读入口。费用金额核算及用户明确配置的金额上限仍按 NFR-04 单列。

**NFR-04｜事件与成本。** 尽量用事件触发结果回流，避免轮询时不断调用模型。记录实际可取得的调用用量与缓存统计；未知成本保持未知。Codex 用量与 DSH 内模型用量分别核算，不能假定现有 bot 日预算已覆盖 Codex。

**NFR-05｜并发与恢复。** 多实例/作业不能覆盖较新状态、重复计分、重复发送或提交已取消的旧结果。区分操作已结束与副作用已确认；不能靠长期占用执行槽来无限阻塞全部后续工作。

**NFR-06｜隐私与身份。** 人物依据平台真实账号识别。内部记忆使用、对外披露、账号操作和管理员诊断分别定义权限。亲密关系分数、昵称和第三方资料不能自行授予权限。

**NFR-07｜迁移与数据生命周期。** 保留合法现存经历和来源，不以重置数据库替代迁移。尊重已有删除和遗忘结果，不从旧记录重建已清除叮嘱。用户此前在清理事项中明确不需要备份与恢复；本次文档不新增备份或恢复任务。迁移的校验、故障回切与临时数据处理须在设计中说明，不能把参考清单里的永久备份、封存或恢复旧记忆当成已批准要求。

**NFR-08｜验证真实体验。** 确定性测试、真实接入验收和连续交互评估分别提供证据。不能用测试脚本强制安排“她关心主人/决定探索”再宣称自主体验达标。

## 5. 参考清单的采纳范围

## 6. 已有设计需要接手 agent 重新评估的地方

1. `memory-design.md` 主要讨论统一目录和当前受众可见检索。必须补清 CONT-01/02 的内部近期活动连续性，避免仍然表现为“另一个窗口不知道我刚做过什么”。
2. 该设计拟收敛多套人格，符合最新方向；迁移不能简单拼接私人文件。人格底色、人物态度、私人事实和条件性表达要求应分别安置。

## 7. 验收场景

下表是后续设计必须映射的用户场景，不预设具体实现。各阶段需注明覆盖范围与仍未完成的部分。

| 场景 | 应观察到的结果 | 关联需求 |
|---|---|---|
| 和用户聊完后转到另一窗口，再回原窗口 | 身份一致；可以接续合法旧话题，无需重复介绍自己 | ID-01/02、MEM-01/03 |
| B 站阅读或 QQ 后台工作完成 | 近期活动能被自己接续；只向适当受众分享适当内容 | CONT-01/02、ACT-02 |
| 不同人物与她交流 | 基本性格一致，态度依据真实人物和经历不同；不切出另一个角色 | ID-02、MEM-06 |
| 用户修改基础人格 | 新版本实际生效；哈希正常改变；授权修改不被固定哈希阻止；原经历保留 | ID-03/05/06 |
| 多次阅读、游戏或创作后再次遇到相关话题 | 能引用真实经历说明选择；不编造体验，不机械建立永久规则 | ID-04、MEM-04/09、ACT-04 |
| 一次唤醒后连续阅读、发送、处理结果 | 可继续行动，能自行结束；用户可以插话或叫停 | ACT-01/05/07 |
| 用户暂时没回复 | 不推定授权、满意或拒绝；不会按固定模板反复追发 | ACT-03/07 |
| 用户纠正原话或明确遗忘 | 旧解释失效；摘要、画像、在途结果和缓存不使其复活 | MEM-04/05/09 |
| 图像/语音作业返回多个结果或重启恢复 | 真实状态可查；同一表达和素材不重复发送 | CONT-03/04、EXP-06、NFR-05 |
| 自定义 QQ 表情的端到端使用 | 素材与发送类型正确；收藏和发送分别有证据；普通图片不能冒充完成 | EXP-04/05 |
| 成年角色当前没有亲密意愿、有意愿及遇到服务限制 | 原因可区分；可以拒绝或主动邀请；用户叫停后不继续 | INT-01/02/03/04/05 |
| 发起 Codex 咨询、追问、中途断开及取消 | 接到正确会话，QQ 保持可用；结果一次回流；未知状态不盲重发 | ENG-02/03/04 |
| 长期运行、重复唤醒、同义任务反复出现 | 有效状态不膨胀为重复任务与叮嘱；工程材料不持续挤占日常交流 | MEM-09、ACT-06、ENG-01、NFR-02 |
| 供应商实际容量不足与读取超长材料 | 不另设软件 token 配额；显式标明覆盖及继续入口，仍可取回原文，不丢否定和状态 | MEM-08、NFR-03 |

“活人感”和“关心”需要用一段连续、包含普通闲聊和实际经历的交互评估；不得只用回复长度、主动消息数或关系分数达标代替。

## 8. 后续概要设计与详细设计交付要求

### 8.1 开始设计前

全面梳理项目的业务代码、文档、数据来源及运行链路，并记录实际核实范围。至少覆盖人格、关系、记忆、连续性、上下文组装、任务、唤醒、工具派发、媒体/表达、送达、恢复、成本及专用 DSH/Codex 接点。无需机械读取虚拟环境和依赖生成物，但不能只读两个方案就宣称通读项目。

核对当前真实 schema、入口和运行版本。区分已有能力、已实现但有缺陷的能力、只有设计的能力以及新的需求。工作区可能有其他 agent 的改动，先核对，不覆盖或清理。

### 8.2 概要设计

建议单独交付 `docs/life-overview-design.md`，至少包含：

- 目标、范围、现状差距与需求编号映射。
- 一个身份下人格、记忆、人物关系、近期活动和任务的职责划分。
- 内部可使用记忆与当前受众可披露内容的处理方式。
- 主动生活及事件驱动执行的整体流程，包含休息、插话、等待与取消。
- 工程工作向 Codex 委派的范围、咨询与实际发布之间的关系。
- 可选实现比较、复用现有能力的理由及主要取舍。
- 分期交付、依赖、风险、各阶段可观察行为与退出条件。

### 8.3 详细设计

建议单独交付 `docs/life-detailed-design.md`，至少包含：

- 实际模块、接口、数据模型、索引及迁移方案；标注哪些接口是已有、哪些拟新增。
- 身份、授权、记忆检索/原文读取、来源链与可见性流程。
- 近期时间线、人物理解和成长材料的写入、使用、纠正、失效及清理规则。
- 上下文分层与实际模型请求结构、用量观测、摘要及原文继续读取方式；无软件 token 配额或节省 token 专项。
- 唤醒、连续活动、后台执行、插话、重复调用、未知结果、取消与重启恢复时序。
- 表情发送及 Codex 咨询的端到端流程、幂等和失败处理。
- 人格版本变更与并发处理，明确用户可编辑性；成年角色意愿和执行限制的区别。
- 配置、观测指标、测试、真实接入验收及需求到验收的追踪矩阵。
- 所需数据操作、与已删除数据的关系、故障回切办法及当前授权范围内不能完成的部分。

先完成设计，不能把本次需求整理解释成对生产修改、数据库迁移、账号操作或对外发送测试消息的执行指令。

## 9. 需要在设计中明确的决策点

以下尚未被用户定为具体实现，agent 应给出推荐方案、依据和待决影响，不能擅自写成已确认要求：

1. 内部可用的统一记忆、跨窗口活动状态与对外披露如何分层，尤其是第三方私聊与管理诊断。
2. 用户设定与经历生长的存放、更新和冲突处理方式；哪些变化走正式人格编辑，哪些属于可纠正的学习材料。
3. 统一人格迁移时如何保留用户私人表达偏好，并防止私人内容被加载给其他联系人。
4. 如何保留有效经历而控制记录、摘要、索引和作业的长期体积；备份、封存和临时副本策略不得默认采纳参考宣言。
5. 自主活动节奏、事件触发与成本之间的权衡；不把固定拒绝概率、固定关心配额或日常刷视频数量当成既定需求。
6. Codex 会话如何管理、用哪个已配置模型、能够执行到什么范围，以及两套调用用量如何呈现。
7. 检索质量、响应时延及长期运行评估的可执行指标。既有设计中的建议数值需要实测依据，0.5 秒不是当前硬指标。
