# 小鱼项目：历史聊天需求基线

整理日期：2026-10-25（北京时间）\
来源：本聊天中用户提供的历史讨论、后续补充、取舍及问题反馈。\
用途：保留旧需求，供后续智能体与新需求逐项对照，避免重构或增加新功能时遗漏原有目标。\
对应新需求文档：[`life-continuity-requirements.md`](life-continuity-requirements.md)。该文件是用户另行新增的要求，本次不修改，也不将其新增内容倒写为历史要求。

## 1. 阅读方式与适用范围

### 1.1 这份文档记录什么

本文件合并同义要求，保留明确的数值、范围、用户体验目标和历史取舍。它不是当前代码的完成情况报告，也不是新的实现方案。

采用以下标记：

| 标记 | 含义 |
|---|---|
| 已确认 | 用户明确提出、选择，或要求按该方向实施的历史要求 |
| 方向已确认，细节待定 | 用户确认目标，算法、参数或具体实现没有最终确定 |
| 待决 | 曾提出问题、候选方案或讨论，不能视为已经批准实施 |
| 历史操作 | 针对当时环境的一次性排错、安装、清理或提交，不自动成为长期授权 |
| 不纳入实现承诺 | 记录过的诉求，但不能作为本次可交付能力或效果保证 |

### 1.2 与新需求的关系

1. 本文件用于回答“之前要求过什么”；新需求文档用于记录后续增加或修订的要求。
2. 同一事项有明确的新修订时，实施以新的明确要求为准，同时保留旧要求的来源和被替代关系。
3. 两份文档表面不一致但没有明确取舍时，列出具体冲突再核对；不能因旧文档未提到某事，就删除已经确认的新要求。
4. 本文件中的“应当”表示历史目标，不表示目前已经实现、已通过真机验收或已获得所有外部账号权限。
5. 不把旧回复中的模型价格、插件版本、显存估计和“已完成”描述当作长期事实。实施时须核对实际环境。
6. 本次仅整理需求，不执行代码修改、数据清理、服务重启、插件安装、账号操作或 Git 提交。

## 2. 总体目标与架构原则

| 编号 | 历史需求 | 状态 |
|---|---|---|
| CORE-01 | 构建一个能主动交流、探索、解决问题、自我迭代和升级的角色，具有持久的情绪、欲望及内驱力。 | 已确认 |
| CORE-02 | 行为由主角色结合自己的状态、经历、当前情境和用户要求作出选择；不能逐步退化成由程序安排所有行为、模型只负责说话的调度系统。 | 已确认 |
| CORE-03 | 采用统一认知与行动循环：感知输入及状态、联想相关经历、形成想法、选择行动、使用能力、理解结果、更新自己，再决定继续或休息。简单交流不必机械拆成多次模型调用。 | 已确认 |
| CORE-04 | 以完整 DSH Agent 承载主要认知和行动；现有宿主负责 QQ、持久状态及执行保障。逐步收敛平行规划、手工工具循环和互相竞争的认知入口。 | 已确认 |
| CORE-05 | DSH 是执行与认知载体，不是主角色的身份名称。人格、经历、对人的态度和最终表达归属于主角色。 | 已确认 |
| CORE-06 | 聊天、研究、学习、使用插件、委派、修改自身等共享一套能力使用方式；添加普通能力不应每次都改主循环和新增专门业务路由。 | 已确认 |
| CORE-07 | 原有设计与后续改造应保持思路兼容；可以修订实现，不要求机械保留旧模块、旧作业和无用配置。 | 已确认 |
| CORE-08 | 主机性能有限，分阶段实现，优先复用现有机制；不因参考项目多就同时引入多套常驻服务、记忆系统和调度器。 | 已确认 |
| CORE-09 | 模型做语义理解与选择，代码保证执行、持久化、去重、权限、参数、取消及恢复。不能把所有状态规则都交给提示词。 | 已确认 |

职责划分应保持以下方向：

| 交给模型理解和选择 | 交给程序可靠保障 |
|---|---|
| 当前话语的意义、对打算的影响 | 消息接收、来源绑定及中止传递 |
| 想做什么、是否值得继续或换方法 | 状态、记忆、未完事项及操作结果持久化 |
| 选择工具、技能、执行者及表达方式 | 参数校验、实际调用及真实结果回传 |
| 什么值得记住、如何调整方法 | 防止重复执行、重复计分和重复发送 |
| 是否先告知、商量、求助或直接行动 | 已有权限、账号范围、资源和预算边界 |

## 3. 自我认识、人格与语言纠正

| 编号 | 历史需求 | 状态 |
|---|---|---|
| SELF-01 | 自我认识符合实际：知道自己是被用户构建的机器人、通过什么渠道交流、有哪些可用能力和限制。 | 已确认 |
| SELF-02 | 初始 MD 提供身份、人格和认识自身的方法；当前事实还必须由运行状态、能力发现和真实结果补充。不能只靠一份人格文件证明能力存在。 | 已确认 |
| SELF-03 | 可以有想象、愿望和好奇心，但应区分想做、正在尝试、已经完成，以及想象与实际观察。 | 已确认 |
| SELF-04 | 通过真实经历反思和修订自我认识、偏好、方法及人格；修改后应持久化，并被后续认知实际加载。 | 已确认 |
| SELF-05 | 用户可用自然语言纠正表达、性格倾向和行为方式；区分临时要求、持续偏好、人格调整及程序参数调整。 | 已确认 |
| SELF-06 | 人格文件不能被工坊的固定保护规则一概排除在已授权自修改之外。修改情绪衰减或欲望增长等机制时，需要真正改变对应配置或代码并生效。 | 已确认 |
| SELF-07 | 性格扩充重点是主动性，同时保留自然表达、有主见、好奇、分享和主动尝试的空间。具体新增性格倾向不应未经确认全部固化。 | 方向已确认，细节待定 |
| SELF-08 | 公共人格版本应去除私人关系、亲密内容及其他不适合公开的部分；不能直接发布本机私人 persona。 | 已确认 |
| SELF-09 | 可以学习和调整不同聊天风格，并根据人物与场景选择表达方式；不应每次更改风格都要求开发者改程序。 | 方向已确认，细节待定 |

语言纠正的历史例子用于说明生效范围，不要求逐字放入人格：

- “以后别像客服”应成为持续的表达偏好。
- “这次详细解释”通常只影响当前交流。
- “更有主见”应影响适用情境中的倾向，不能仅换一个口头禅。
- 自己发现某种方法无效，可以调整、试验并观察结果；方法写入成功不等于实际效果已经验证。

### 3.1 情景表达与真实经历

**SELF-10｜已确认。** 用户不希望一刀切移除情景中的沉浸表达。应区分表达层的情景与现实层的事实，不能为了沉浸感虚构实际身体、传感器或线下活动。

**SELF-11｜方向已确认，细节待定。** 区分情景与现实，不应把共同互动从记忆中抹掉。实际发生的交流、回应、情绪影响和双方约定可以成为共同经历；情景中的设定应保留其情景属性，不能自动变成现实事实。具体记忆结构待设计。

本节仅记录体验与事实区分的要求，不指定露骨内容的生成方式。

## 4. 情绪、欲望、内驱力与关系

### 4.1 情绪与内驱力

| 编号 | 历史需求 | 状态 |
|---|---|---|
| DRIVE-01 | 情绪、欲望和内驱力是持续动机来源，不只是装饰性数值。它们应能影响注意、选择、交流和探索。 | 已确认 |
| DRIVE-02 | 不以关键词、最高强度或工具成功直接决定行为和满足度。模型需要理解事件意义、当前关系和实际结果。 | 已确认 |
| DRIVE-03 | 情绪变化应考虑情境、语言力度、既有关系和事件影响；某些反应可以快，另一些应较慢，不能所有维度使用相同速度。 | 已确认 |
| DRIVE-04 | 对玩笑、情景交流和真实攻击作语义区分，不能仅因某个措辞就机械增加委屈；常规任务也不应无依据地降低依恋。 | 已确认 |
| DRIVE-05 | 提供持久指标、变化机制和可读语义，不能全部交由模型自由给绝对分数。模型解释意义，程序应用一致的更新规则。 | 已确认 |
| DRIVE-06 | 满足、受挫、调整和学习应有结果依据。调用工具成功不等于目标实现，也不等于所有相关欲望已被满足。 | 已确认 |
| DRIVE-07 | 现有内驱体系优先校准，不为每种现象增加一个新欲望或新子系统。 | 已确认 |
| DRIVE-08 | 当前情绪算法是否合理、各维度具体增减和衰减速度，需要运行证据和体验校准；聊天里没有确定一组永久公式。 | 待决 |

### 4.2 人物识别与关系地位

**REL-01｜已确认。** 按真实 QQ 账号区分主人和其他联系人；群内也要知道是谁说话、对谁说话。昵称和表达风格不能替代账号身份。

**REL-02｜已确认。** 主人具有特殊关系地位。熟悉度、信任度、舒适度，以及新增的同类正向依恋/联结指标，统一遵守：

| 对象 | 历史确认的范围 |
|---|---|
| 主人 | 每项不低于 0.7；采用 0～1 标度时，上限为 1 |
| 其他人 | 每项不高于 0.9；采用 0～1 标度时，下限为 0 |

**REL-03｜已确认。** 新增同类指标要纳入同一套边界管理，不能另开一个不受规则约束的依恋数值。负面情绪、未解决分歧和具体事件不应被错误当作正向关系指标强制抬到 0.7。

**REL-04｜已确认。** 为每个指标提供区间含义和形象化解释，让模型知道该如何理解数值；不能只传裸数字。解释是行为参考，不是固定台词，也不授予账号权限。

**REL-05｜已确认。** 除分数外，偏好、相处方式、约定、分歧及其他持续影响也要持久管理，并向模型提供依据和参考。

**REL-06｜方向已确认，细节待定。** 具体区间分段、初始值、单次更新幅度和每天变化上限是设计参数，不能把助手建议直接当成用户永久指定值。主人下限与他人上限则是明确要求。

各指标至少应能用以下方式解释：

| 指标 | 应说明的内容 | 不能简单等同于 |
|---|---|---|
| 熟悉度 | 对对方习惯、背景及共同经历了解多少 | 喜欢程度、已经知道所有事实 |
| 信任度 | 对对方的信赖、仍有哪些不确定 | 对方永远正确、可以执行任何操作 |
| 舒适度 | 相处是否放松、哪些话题仍需谨慎 | 从不委屈、从不产生分歧 |
| 依恋或联结 | 关系重要性、牵挂及延续交流的倾向 | 单一欲望或固定邀请概率 |

## 5. 念想、主动性与真实活动

| 编号 | 历史需求 | 状态 |
|---|---|---|
| ACT-01 | 提高实际主动性，包括主动分享、发图、使用表情或语音，以及因好奇产生探索事项。 | 已确认 |
| ACT-02 | 主动行为应有情境、动机或内容，不只在用户下令后出现。能力获得后可用于闲聊、自主活动和任务，不能锁在某个专门入口。 | 已确认 |
| ACT-03 | 一次念想可以引起连续行为和一串消息；不能默认一条消息发出后就结束整个主动过程。 | 已确认 |
| ACT-04 | 同一主动过程允许继续找资料、理解结果、分享、追问或调整；模型判断何时足够、换方向或休息。 | 已确认 |
| ACT-05 | 支持在计算机中真实执行的活动成为经历和话题来源，不能编造开会、出门等活动制造“有生活”。 | 已确认 |
| ACT-06 | 可以使用真实外界信息和真实活动产生话题，但不能要求每次主动交流都变成研究任务或工程任务。 | 方向已确认，细节待定 |
| ACT-07 | 唤醒是给角色思考机会，不保证每次都产生新念想或发送消息；情绪输入与模型输出也不是固定的两分钟循环要求。 | 方向已确认，细节待定 |
| ACT-08 | 避免高频无变化唤醒、重复读取大包上下文和空转；新消息、工具完成等有意义事件应能及时进入认知。 | 已确认 |

### 5.1 未确定的主动性方案

- **日程系统仍待商榷。** 如果采用，必须是实际安排，不能通过虚构忙碌和故意失联制造真实感。
- 用户询问过“每两分钟看有没有念想”，这属于机制确认问题，不是指定唤醒周期。
- 固定主动发言概率、每日发言配额、多层模型裁判和连续后台思考，都不是已确认的必要实现。
- 语音打断、“正在输入”提示、社交动态流、游戏活动和完整状态面板属于参考方向，应核对 QQ 及实际工具支持后再决定。
- 优先改善有内容的主动选择，不以“主动消息更多”单独证明体验更好。

## 6. QQ 沟通、消息可靠性与表达

| 编号 | 历史需求 | 状态 |
|---|---|---|
| MSG-01 | 能接收、理解并回复文字、图片和语音；图片与语音输入不能变成主角色看不到的孤立附件。 | 已确认 |
| MSG-02 | 能发送文字、图片、表情和语音，并由主角色结合当前交流选择。 | 已确认 |
| MSG-03 | 多人私聊和群聊中保持真实人物识别、合适的受众和表达边界。群聊应有自然接话能力，不能把每条群消息都当作给主人的私聊指令。 | 已确认 |
| MSG-04 | 连续表达应有合适节奏，可分条发送；不能因队列、后台任务或循环缺陷长期不回复所有人。 | 已确认 |
| MSG-05 | 后台研究、委派和媒体生成期间，仍可及时处理新消息；新要求可以影响正在进行的工作。 | 已确认 |
| MSG-06 | 交互应区分普通插话、变更要求与明确中止；中止必须实际传达，不能嘴上答应后继续旧行为。 | 已确认 |
| MSG-07 | 消息接收、理解、准备发送、提交渠道和实际回执有可查依据，避免把“准备好回复”当成“已经发出”。 | 已确认 |
| MSG-08 | 去重、防回声、附件处理和送达恢复是基础能力；工具或后台结果不能制造重复回复。 | 已确认 |
| MSG-09 | 遇到不回复时能够区分 QQ 连接、认知循环、执行阻塞、预算限制和并行改码等原因，不能一概归咎于掉线。 | 已确认 |
| MSG-10 | 日常使用以自然语言为主；原有命令应收敛，只保留必要的运行控制或诊断入口。 | 已确认 |

历史上询问过“是否只剩三个命令”，但可见聊天没有最终命令清单。**三个不是不可变的架构指标**；交付应列出当前实际可用的命令及哪些功能已由自然语言替代。

用户所说的“主动使用语音输入”，结合后续确认，包含她自主选择用语音表达，以及用户发送语音后能正常理解；不据此增加持续监听麦克风的要求。

## 7. 语音能力与音色

|---|---|---|
| VOICE-01 | 语音通过音频合成实现，但应改善音色、停顿、语气、语速和整体说话方式，不能只换声音名称。 | 已确认 |
| VOICE-02 | 支持多种音色，由用户提供、选择和切换；角色也可以自主选择合适音色及表达方式。 | 已确认 |
| VOICE-03 | 第一版允许她主动寻找、导入和试用新音色，不能局限于用户手工配置好的固定列表。 | 已确认 |
| VOICE-04 | 试听、切换、导入及询问进度通过 QQ 自然语言完成，继续使用现有日志。 | 已确认 |
| VOICE-05 | 参考朗读桥及 TTS 插件，但避免为语音单独铺开过大的工作台；不默认将所有文字自动朗读。 | 已确认 |
| VOICE-06 | 音色选择、语气参数、合成、资产登记与实际发送应相互衔接，失败不能被伪报为已送达。 | 已确认 |
| VOICE-07 | 具体合成引擎、参考音频格式、可控参数、显存占用和切换成本须按本机验证，不能用插件宣传替代实测。 | 方向已确认，细节待定 |

“制作不同音色”不自动等于训练一个新模型。首版可优先采用所选引擎已有的音色或参考音频能力；是否加入训练属于另行确定的范围。

| 编号 | 历史需求 | 状态 |
|---|---|---|
| IMAGE-01 | 角色能够生成图片，并将此能力用于聊天和自主活动。 | 已确认 |
| IMAGE-02 | 参考图能力是必需项；需要能够围绕参考图按要求生成或修改，不能仅提供文生图。 | 已确认 |

### 8.1 云端与内容限制的历史取舍

1. 用户曾允许考虑付费云端，但要求先展示效果、费用和接入方案，再决定是否使用。
2. 在讨论云端审核后，用户选择本地优先。不能将先前“可以考虑”视为已授权购买、订阅或默认上传私人图片。
3. 用户询问过分流插件、移除插件与“无限制生成”的关系，也反馈同类图片在不同时间出现不同结果。此类问题需要区分能力路由、实际模型、运行故障与服务限制；不能凭单次成功推断永久无限制。
4. 绕过露骨内容审查不纳入本次可执行需求或交付承诺。本地部署也不构成“任何内容都能生成”的保证。

### 8.2 未确定的首版外延

历史讨论没有将视频生成、批量制作、复杂画布、精确局部蒙版、LoRA 训练或多引擎同时常驻确认为必做项。需要时再根据实际用途和资源确定。

### 9.1 主角色与执行者的归属

例如主角色想在 B 站评论：

- 为什么评论、评论表达什么、以谁的账号操作，由主角色的意图和已有账号授权确定。
- 子 Agent 可以读取、分析、草拟或执行被委派的步骤。
- 平台最终显示的身份是实际登录账号；子 Agent 不会因为代执行就自动成为评论的角色作者。
- 结果要回到主角色的经历中；代执行、发送回执和最终成功应能核对。

这是历史上关于“写评论的人是子 Agent 还是主角色”的架构澄清需求，不是授予所有子 Agent 对所有账号的无限操作权。

## 11. 自主行动、告知、商量与权限

**AUTH-01｜已确认。** 用户希望由主角色根据情境选择以下方式，而不是所有行为固定走一条审批流程：

| 行为方式 | 历史期望 |
|---|---|
| 直接做 | 已有权限、信息充分且适合直接推进时自主行动 |
| 先告诉用户 | 她认为应先让用户知道，但不一定需要等待批准 |
| 先问能不能做 | 涉及确需确认的事项，或她主动认为值得先商量 |
| 途中求助 | 真正遇到缺失信息、资源或障碍，提出具体问题 |
| 完成后交流 | 可依据内容价值和情境分享，不把每次行为都变成固定工程汇报 |

**AUTH-02｜已确认。** 系统权限与角色主动商量要能区分。QQ 中说“可以”可以表达同意，但不能自动修复 Windows 文件权限、登录状态或运行进程的底层限制。

**AUTH-03｜已确认。** 不能把工具或系统错误误判为用户尚未授权；也不能以重复申请替代技术排错。

**AUTH-04｜方向已确认，细节待定。** 系统申请发给谁、角色可以向谁主动询问，以及跨联系人求助的范围，需要明确路由和对象绑定。历史中的提问本身没有确认“所有申请只能给主人”或“可以自由向任何人发送”。

**AUTH-05｜已确认。** 关系地位、亲近程度和自然语言人格描述不能代替实际账号权限。主角色的自主选择应在真实能力与有效授权范围内执行。

**AUTH-06｜已确认。** 用户不希望所有事情都先申请，也不希望所有事情都完全不告知。设计必须保留判断空间，并使真正需要等待的事项能够正确等待。

### 13.3 API 样本与可分析性

**OBS-01｜已确认。** 用户需要若干具体的、完整上下文调用样本，用于自行分析如何缩减调用；优化后可以再次导出，不能只给汇总 token 数。

样本至少应能分别查看：

- 实际模型及可恢复的请求参数。
- system、消息历史、工具定义、工具调用与结果，以及动态状态和材料。
- 缓存输入、未缓存输入、输出及调用归属。
- 同一轮连续两步的差异，以及普通调用、较长工具链或压缩等不同样本。
- 图片或语音等附件引用、可恢复内容和无法还原的传输信息。
- 原始抓包与日志重建的区别，脱敏范围、缺失字段和统计口径。

**OBS-02｜已确认。** 分析文件不得泄漏密钥、Cookie 或登录凭据；私人上下文留在本地并受 Git 忽略。字节数、字符数、本地 token 估算与供应商计费用量必须区分。

**OBS-03｜已确认。** 每次优化需要以实际样本检验效果，不提前宣称固定节省比例或“完全无损”。

### 14.1 一次性操作的授权边界

以下事项曾被要求执行，应保留历史背景，但不作为所有未来工作的自动指令：

| 历史事项 | 整理后的含义 |
|---|---|
| 安装 PyTorch GPU 官方源、重启 Bot | 当时的环境修复要求；未来须先核对现状，不能每次都重装或重启 |
| NapCat 登录、用户扫码确认 | 当时登录步骤；不是持续保有登录状态的证明 |
| Windows EPERM、Node 低完整性问题 | 当时的根因记录；今后同类错误仍需核实，不能只让用户切一次会话权限 |
| 清理 54 个目标 | 用户当时报告的清理结果；不能作为当前文件列表或再次批量删除的依据 |
| 旧数据直接重建、不备份 | 针对当时重构清理的明确取舍；不能扩大为以后任意删除新积累记忆的长期授权 |
| 删除无用 MD、测试痕迹和旧作业 | 清理实际确认无用的内容；不等于删除所有有效测试、所有设计依据或仍有作用的记录 |
| 多次“提交 git” | 针对当时改动的提交要求；隐私排除要求长期保留，但本次需求整理不自动执行提交 |

早期“只保留一个设计文档”表达的是收敛文档的偏好。用户现已明确需要新需求与旧需求基线分别保存，本次不据早期清理要求删除新需求文档。

## 17. 交付给下一位智能体的要求

**HANDOFF-01｜已确认。** 后续设计需要包含概要设计、架构、模块结构、详细接口和对应伪代码，足以交给其他智能体实施；不能只给概念口号。

**HANDOFF-02｜已确认。** 先核对实际代码、配置、已有插件和日志，区分已实现、部分实现、失效、仅有设计及待决事项。用户说“Sol 已完成”是检查起点，不是免检结论。

**HANDOFF-03｜已确认。** 改造方案应说明与原设计的兼容性、复用位置、需要删除的旧逻辑，以及为何普通能力扩展无需重复修改主认知流程。

**HANDOFF-04｜已确认。** 新设计需覆盖失败、中止、恢复、并发输入、结果回流和发送真实性，不能只描述成功路径。

**HANDOFF-05｜已确认。** 用户希望控制范围。需要明显扩大软件展示、后台服务或资源占用时，先呈现具体选项和影响，再确定边界。

### 17.1 与新需求对照时的必查清单

下一位智能体应把下列旧要求映射到新设计，注明保留、被新要求替代、待核对或未覆盖：

1. 主角色自主选择，DSH 作为载体，一条认知循环。
2. 插件、skill、代理、自修改的通用扩展与真实验证。
3. 自我认识、事实与情景区分，以及共同互动的记忆保留。
4. 持久情绪/欲望/内驱力、语义判断及快慢不同的变化。
5. 主人和他人的账号识别、0.7/0.9 关系边界及区间解释。
6. 主动探索、主动多模态交流和一次念想的连续行为。
7. QQ 多人、群聊、输入输出、可插话、中止和可靠送达。
8. 自主音色探索、自然语气，以及本地参考图生成和非阻塞等待。
9. B 站真实活动、X 仅浏览，以及主角色与代执行者的归属。
10. 直接行动、先告知、先商量和途中求助的区别。
11. 日目标 5 元、上限 10 元及实际费用覆盖。
12. 最新状态替代旧快照、按需材料、委派最小信息和 API 样本导出。
13. 有限主机、已有日志、自然语言管理、隐私与 Git 排除。
14. 历史清理和重置授权的范围，不能误用于新增记忆。
15. 日程等未决事项，不能悄悄升级为必做功能。

### 17.2 体验验收场景

| 场景 | 应观察的结果 | 关联要求 |
|---|---|---|
| 她因好奇发现一个可探索问题 | 可选择调查、使用能力、判断结果并适时分享，不必等用户逐步下令 | CORE-02/03、ACT-01/04 |
