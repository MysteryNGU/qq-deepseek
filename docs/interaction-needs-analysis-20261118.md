## 1. 需求 1：插话（云端未实现，t13 在做）

### 1.1 现在只有「关键词打断」，没有任何「插话」概念

云端唯一相关的东西是这一行正则（云端 `life/companion.py:1780`，已用 grep -n 核实）：

```python
INTERJECTION = re.compile(r'^(停|停一下|等等|等一下|打住|别说了|先别|stop\b)', re.I)
```

命中时取消未发气泡并 cancel 正在跑的模型请求。**没有前缀的消息不产生任何「被打断过」的记录**，
她下一轮也就无从知道自己说话时有人插过话。

### 1.2 设计要点（给 t13 参考，不是现成实现）

现有的输入合并循环 `_input_loop` 已经保证「她回答期间来的消息会排队、不会被丢」，
所以需求 1 要补的**不是消息不丢**，而是**让她知道这件事发生过**。要点：

1. **只记录，不打断。** 收到消息时若她正在回答，记一条插话事实；**绝不 cancel 模型调用**。
   打断只保留给「停/等等」那条正则。
2. **带进下一轮，消费即清空。** 不能每次醒来都重复出现。
3. **带时效。** 超过 5 分钟才被消费的，要说明成「较早的插话」，不能让她以为是刚发生的
   （和 watchdog 那次「状态过了时效还在按原样呈现」是同一个教训）。
4. **要有 boundary 依据可回查。** 每条插话应带 event id，否则她事后无法回查「是哪几条」。

> 说明：§1.2 的 1–4 是设计要求，**不是对现有代码的描述**。
> 初版把这几条误当成「已实现」，见 §6。

## 2. 需求 2：她中途收回未发的气泡（缺口：没有出口）

### 2.1 机制现状

`_cancel_pending_bubbles(reason)` 在云端 `life/companion.py:625`，做得是完整的：
清空 `bubble_outbox`、把台账标 `CANCELLED`、记一条 activity、唤醒发布循环。

### 2.2 实测：只有两处调用，都是系统发的

```
云端 grep -n _cancel_pending_bubbles life/companion.py
551:        self._cancel_pending_bubbles('restart')
625:    def _cancel_pending_bubbles(self, reason):
1761:            self._cancel_pending_bubbles('interjection')
```

`551` 构造时、`1761` 用户喊停。**角色没有任何工具能调它。**
`drop_remaining` 在云端同样不存在（0 处）。

### 2.3 缺口的本质

她能决定「说什么」，不能决定「还说不说」。缺口就是一个出口：

```
kind: bubble  op: drop_remaining   （或并入现有工具的 op）
```

内部直接复用 `_cancel_pending_bubbles('self_withdraw')` 即可——**函数已经是对的**，
不需要新写清理逻辑。

### 2.4 三个必须先定的语义问题（产品判断，不是实现）

**Q1：她什么时候来得及调用？** 发布间隔 1–5 秒。她一轮结束后要能发起下一个动作，
才谈得上「中途」。→ 建议先量「一轮里从第一个气泡入队到最后一个发完」实际跨多久。

**Q2：全清还是部分清？** 现函数是**全清**。要部分收回就得改签名。
→ 建议先只做全清（「剩下几条不说了」正好对应全清）。

**Q3：已发的收不回来。** 只动 `bubble_outbox` 里没发的。
→ **必须写进工具定义**，否则她会宣称「我收回刚才那句」而那句已经发出去了。

### 2.5 风险

| 风险 | 说明 |
|---|---|
| 滥用全清 | 犹豫时反复清空，说话变得断断续续 |
| 取消与发送竞态 | `mark_sending` 之后、`mark_sent` 之前取消会落到 `UNKNOWN` 语义，台账记「结果未知」而不是「已取消」 |
| 与「用户喊停」撞车 | 两者调同一函数，需 `reason` 能区分（现已是参数，安全） |

## 3. 两项需求的关系

需求 1 的「关键词打断」路径和需求 2 的「自我收回」调的是**同一个函数**。
需求 2 落地后，`_cancel_pending_bubbles` 会有三类调用者（启动 / 用户喊停 / 她自己），
`reason` 必须能区分——审计记录已带 `reason`，但要确认回查界面能读出来。

## 6. 教训：我为什么把「未实现」读成了「已实现」

**这是本文最该留下的一节。**

### 6.1 我做错了什么

我读了 `C:\Users\76328\qq-deepseek\life\companion.py`，看到 `_interjections`、
`_interjection_view`、`state['interjection']` 都在，就断言「需求 1 已实现」，
还给了 `:505-507`、`:1813`、`:1597-1599`、`:707-736` 四处行号。

**但那是本地工作区，不是云端生产。** 实测对比：

| | 本地工作区 | 云端生产 |
|---|---|---|
| md5 | `e0c5f8c4…` | `837513ab1d01b7e495d6fb69ca4648ff` |
| 行数 | 3392 | 3339 |
| `_interjections` | 4 处 | **0 处** |
| `state['interjection']` | 1 处 | **0 处** |

而且这几段是**未提交的工作区改动**（`git status` 显示 `M life/companion.py`，
diff 里 63 行新增），来源不是云端。

**行号也对不上**：因为本地文件比云端多 53 行，我给的 `:707-736` 在云端对应的是
`_emit_phase`/`_persona`，完全是另一段代码。

### 6.2 正确的做法

**断言「某段代码存在/已实现」，必须同时给出可复跑的证据，而不是行号。**
行号是最容易跟着文件版本漂移的东西。今晚这已经是第三次同类错误
（前两次是「云端有 lifecycle 模块」「手机从没发注册请求」），共同点是
**印象中的代码 ≠ 真实的代码**。

最低要求，二选一：

```bash
# 方式 A：grep 原文（最直接）
grep -n '_interjections' /opt/qq-deepseek/life/companion.py || echo 'NOT FOUND'

# 方式 B：先钉版本，再谈行号
md5sum /opt/qq-deepseek/life/companion.py && wc -l /opt/qq-deepseek/life/companion.py
```

**并且要说清楚查的是哪一份文件**：本地工作区、本地 HEAD、还是云端生产。
三者可以完全不同——今天就是这样。

### 6.3 复跑本节结论

```bash
# 云端
md5sum /opt/qq-deepseek/life/companion.py   # 期望 837513ab1d01b7e495d6fb69ca4648ff
grep -c '_interjections' /opt/qq-deepseek/life/companion.py   # 期望 0
grep -c 'drop_remaining' /opt/qq-deepseek/life/companion.py   # 期望 0
grep -n '_cancel_pending_bubbles' /opt/qq-deepseek/life/companion.py  # 期望 2 处调用 + 1 处定义
```

一旦云端 md5 变了，本节的所有数字都要重新核对——**这就是为什么证据要比行号稳**。
