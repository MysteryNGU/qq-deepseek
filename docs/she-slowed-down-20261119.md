# 她"变慢"了吗：吞吐恒定、输出膨胀（2026-11-19）

## 结论（一句话）

**模型吞吐六天没变（`out/秒` 稳定在 123~175）。变的是她每次的输出长度——
`output_tokens` 从 177 涨到 913（dialogue）、从 189 涨到 1601（activity），
其中 activity 有 84.7% 的调用超过 1000 token。**

**秒数和输出长度高度线性：`seconds ≈ 2.09 + 0.00377 × output_tokens`，R² = 0.78。
上下文长度（`input_tokens`）与耗时几乎无关，R² 只有 0.18。**

## 模型吞吐稳定的证据

**`out/秒` 六天如一日稳定在 130~200（`activity`）/ 123~175（`dialogue`）。**
**这是直接观测，不依赖任何模型假设。**

## 回归：用哪个自变量

**第一次用 `(in+out)` 做线性回归，R² 只有 0.268 —— 看起来"变长解释不了变慢"。**

**但那是自变量选错。改成 `out` 单独后：**

| 样本 | out 单独 | in 单独 | in+out |
|---|---|---|---|
| ALL (n=4333) | **R² = 0.780** | 0.179 | 0.268 |
| dialogue (n=813) | **R² = 0.679** | 0.121 | 0.228 |
| activity (n=1730) | **R² = 0.580** | 0.155 | 0.262 |
| work (n=1031) | **R² = 0.831** | 0.137 | 0.257 |

**`seconds ≈ 2.09 + 0.00377 × output_tokens`**

**两个要点：**
1. **`out` 单独解释力 58~83%，`in` 几乎不相关（0.12~0.18）。**
2. **截距 `a ≈ 2.09` 秒 —— 这是首 token 的固定开销，
   与"耗时 = 固定开销 + 生成速度 × 输出长度"这个物理模型吻合。**

**教训：`(in+out)` 作为自变量把两个不相关的东西混在一起，稀释了解释力。**

## 对"优化"的意义（最重要的一节）

**一次 chat 端到端约 20 秒，实测分解：**

```
模型（dialogue）          3 ~ 5 秒
系统（life_recall 1208 SQL）  0.4 ~ 0.5 秒
剩余                     约 15 秒，构成未定论
```

**而系统侧已知的最大技术债是「事件循环里做同步 DB」（主线程 62% 时间）。**

**但即使把它优化到 0，也就省 0.5 秒 —— 对用户感受到的 20 秒几乎没有影响。**

**所以：**
- **不能靠优化 DB 解决"她变慢了"的体感**
- **要改善体感，方向是「减少输出长度」和「搞清楚那 15 秒」**
- **DB 优化本身仍然值得做（`/alive` 会卡 2~19 秒是真问题），但那是另一个问题**

**如果不写清楚这一条，下一个人会花几天优化 DB，然后发现体感没变。**

## 方法上的教训

1. **`(in+out)` 作自变量稀释了解释力** —— 两个不相关的量混在一起，R² 从 0.78 掉到 0.27。
2. **字段名要先看再用** —— `usage` 里是 `input_tokens`/`output_tokens`，
   不是 `prompt_tokens`/`completion_tokens`，第一次查询全返回 0。
3. **按判据验自己** —— R² 0.25 < 0.8 所以撤回"变长导致变慢"，改用 out 单独后 R² 0.78 才成立。
