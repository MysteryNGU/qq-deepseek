# ① 后台进程管理

## 做了什么
`kind=command` 增加五个 op：`start / status / wait / stop / logs`。不带 op 时走原来的同步路径。

- 输出**落文件**，只从尾部倒读 256 KB 取最后 N 行——几百 MB 的日志不进内存
- 进程树整体停：复用 `life/supervisor.py` 的 `ProcessTree`（POSIX `killpg` / Windows Job Object）
- 登记在 `data/companion/background/jobs.json`，重启后仍可 `status/logs/wait`
- `executor.close()` 调 `reap_all()`，服务关闭不留孤儿

## 怎么验的（隔离，8 项全 PASS）
```
B1 start 立刻返回（0.002s）          B5 stop 连孙进程一起杀（关键）
B2 status 报 running                 B6 重启后新实例仍能查到同一 job
B3 logs 内容真在文件里               B7 reap_all 关闭时清干净
B4 wait 结束后 exit_code=0           B4b wait 超时不撒谎（timed_out=true，仍 running）
```

## 发现的 bug：僵尸进程让 `wait` 永远等不完
```
t=0.3s state=S  kill0=ok  Popen.poll=None
t=0.6s state=Z  kill0=ok  Popen.poll=0      ← 已经退出，信号探测还说活着
```
**`kill(pid, 0)` 对僵尸进程也返回成功。** 只看信号探测，一个已退出的进程会被永远当成"在跑"。

修法比修 bug 重要：改成读 `/proc/<pid>/stat` 判 `Z`/`X`，并且**新增 `state=gone`**——
「进程不在了但没留下退出码」是**不知道成没成功**，不写成 finished 也不写成 failed。

## 她自己怎么用的
我说「起个后台命令，睡 20 秒，起完马上告诉我 job_id，不用等」。她自己依次用了
`start → status → logs`，没等就回来了，并说：

> job_id 是 bg_ad06a7e8e7d8，退出码 0，用时 31.5 秒
> **status 只返回运行状态，不返回输出；要看到真实输出，得用 logs 读**

**今晚第一个她自己归纳出用法的工具。**

# ② 任务清单

## 做了什么
新增 `kind=task`，四个 op：`add / update / list / clear`。

**不另建表**：读写的是 `meta.k = 'action_task:<ref>'` 那一行，和她 159 条项目记录同一份。
`T6` 断言 `sqlite_master` 前后完全一致。`clear` **不删数据**，只是默认不列已完成的。

`add` 的核心语义不是"加一条"，是**"这条我做过了吗"**：
同一目标再来一次，回执给 `repeat=true`、次数、上次时间、上次状态、上次卡点、上次下一步。

## 怎么验的（10 项全 PASS）
```
T1 add 只建一行             T4 list 显示"卡了多久 + 做过 3 次"
T2 update 落在同一行        T5 clear 不删数据（2→2）
T3 repeat 检出（核心判据）  T6 没新建表
T3b 标点差异仍算同一件事    T7 空 goal / 非法 status / 未知 ref 均被拒
T3c 不同目标不误判
```

## 发现的三个 bug
1. **`runs` 少算**：第一版数行数，重复 add 不建新行，于是「做过 3 次」显示成「1 次」。
   **这正是这个工具要防的误判本身。** 改成在行上累加 `attempts`。
2. **`add` 记成 `goal='add'`**：我优先取了 `action['goal']`，而执行器给的 goal 是派生的 op 名。
   改成 `arguments.goal` 优先；那条垃圾记录已删除。
3. **`list` 整条崩掉**：生产里有 **`progress` 是列表**的行（存 checkpoint 对象列表，不是次数），
   `int()` 它抛 `TypeError`。**一条历史脏字段把整张清单打翻了。**
   改成只认数字、其它一律当不知道——**一条坏字段不许带走其它任务**。

## 她自己怎么用的
> 这条**已经有过**：补齐技能库三份做法 起共 2 次，最近一次在 18:08（doing），卡了 0秒。
> 上次卡在：other。上次写的下一步：读 task add 回… 先看上次留下的下一步与卡点，**别当作新事从头再来一遍**。

# ③ 结构化提问

## 做了什么
新增 `kind=ask`，四个 op：`ask / pending / answer / cancel`。状态挂在角色的 `_state('pending_questions')` 上，不新建表。

**三个关键设计：**
1. **程序不发消息**。`ask` 只登记问题并把问题文本交回给她，话由她自己说——`A1b` 断言回执里不含发送动作。
2. **主人下一条消息就是答案**。不需要前端配合、不需要点按钮。认领发生在她回话**之前**
   （`chat()` 里 ingest 之后立刻认领），所以她**这一轮**就知道答的是哪个问题，不是下一轮才后知后觉。
3. **超时说清楚**。超过 `expires_in` 未答 → `state=expired`，文案写
   **「没等到回答——这不是拒绝，是没答」**；超时之后才来的回答标 `answered_late=true`。
4. **同一问题不重复问**（复用 ② 的思路）：还挂着时再 `ask` 回 `repeat=true` + 已问次数。

## 怎么验的（10 项全 PASS）
```
A1 ask 登记且有 id/ttl       A4 超时=没等到回答，不是拒绝
A1b ask 不发消息             A4b 超时后的回答标 answered_late
A2 pending 显示等了多久      A5 同一问题不重复问
A7 进入模型上下文            A6 cancel 不等于答过
A3 下一条消息被认领为答案    A8 空 question 被拒
```

## 线上的三个 bug
**注意：这三个都不是我单测能发现的**，是在生产数据上撞出来的。

1. **`progress` 是列表**导致整张清单崩（见 ②-bug3）。是我自己先撞的。
2. **`add` 记成 `goal='add'`**（见 ②-bug2）。
3. **她报「task 带实参就报 TypeError」——我核实后发现是过期的坏记忆**：
   台账里 TypeError 全部发生在 **18:04–18:06**，修复在 18:08 重启后生效；
   她 18:15 说的那句话描述的是十分钟前的旧状态。**我没有直接采信，而是让她重试**：
   ```
   18:1x task op=list completed → 「查主人手机只有副屏一条路｜doing｜卡了 23小时…」
   ```
   **这是"她自己对工具状态的记忆会过期"的第一个实例**——值得记下来。

# 遗留与建议

1. **`ask` 目前不在 `available_kinds` 之外单独可见**——她的上下文里 `ask` 依赖 `_core` 存在才列出，已验。
2. **她对自己工具状态的记忆会过期**（③-bug3）。建议：`memory op=used` 已经是查真实回执的入口，
   但她在描述"工具坏了"时没有先去查。这属于 ①暴露 之外的**习惯**问题，不建议靠改代码解决。
3. `clear` 是只读语义（不删数据），但如果将来要真删，务必先改这里。
4. 后台任务的服务重启后 `exit_code` 可能拿不到——这是如实设计（`state=gone`），不是缺陷。
