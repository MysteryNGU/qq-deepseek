## 二、① 索引是必需路径还是加分项？

**答：加分项。检索有三条路并行。**

```python
# life/life_recall.py:190 附近
routes = [text_route, semantic, related] if mode == 'auto' else (...)
```

| 路线 | 数据来源 | 依赖向量索引？ |
|---|---|---|
| `text_route` | `life_terms` 词法命中 | **否** |
| `semantic` | `life_semantic_index` 向量 | **是** |
| `related` | `find_related`（实体/关系） | **否** |

**而且覆盖度会如实上报：**

```python
semantic, coverage['semantic'] = self.index.search_vectors(allowed, query_vector)
if candidate_refs is not None and coverage['semantic']=='ready':
    ...
    if omitted:
        coverage['semantic']='partial'  # Omitted records are not certified covered.
```

**索引不全时报 `partial`，不会假装全覆盖。**

### 但有一个真实的收窄

```python
# life/life_recall.py:164
if query_vector is not None and qterms and not entity_refs and not actor_refs:
    candidate_refs = set(exact_ids)
    candidate_refs.update(... 已有 ready 索引的资源 ...)
    candidate_refs.update(... life_terms 命中的资源 ...)
```

**在这类「纯文本向量查询」下，既没索引、词法也没命中的资源进不了候选池。**

实测：**3385 个资源既无 v2 索引、也无词法条目** —— 它们在纯文本向量查询下不可达
（但 `exact_ref` / `entity` / `actor` 三条路仍能到达）。

## 四、③ 建不完时，检索能力实际下降多少

**关键数据（2026-11-19 11:25 实测）：**

```
active 资源            14597
已有 v2 索引            1072  (7.3%)
仍在使用 v1 索引        13093  (89.7%)
有词法条目（life_terms） 10999  (75.4%)
既无 v2 索引也无词法     3385  (23.2%)
```

**注意：v1 索引一直都在，不是"没建"。** 89.7% 的资源有 v1 索引可以检索。
v2 只是把 v1 的分片规则修正后重算一遍。

**所以「只建到 40%」的实际影响是：**
- `text_route`：不受影响（75.4% 有词法条目）
- `semantic`：v1 + v2 叠加覆盖，不会掉到 40%
- `related`：不受影响

**下降主要发生在「既无索引、也无词法」的那 3385 条，而它们的文本长度普遍很短
（user message 这类），本来就难通过向量检索命中。**

## 五、代价：这次到底付出了什么

```
CPU：基线 18.5%，峰值 36.2%（round=2）
    round=4 时曾达 58.1~72.6%，超出 30% 红线，已回退到 2
/alive：中位 1.7ms，但峰值可达 5002ms（一次大资源 build 期间）
内存：embedding 进程 RSS 656MB，机器 3.5GB / available 2.2GB
时长：约 12.8 小时（19.0 job/分）
```

**`/alive` 峰值 5 秒这件事，yield 与无 yield 两组都出现（对照组 5002.4ms，
基线组 5002.5ms），说明它不是 build 循环造成的。**

### 对 5002ms 的推理（captain 纠正过我一次）

我最初推断「5002ms ≈ `asyncio.wait_for(x, 5)` 的超时值，所以是某个 wait_for 在等」。
**这是错的。** 区别在于：

```
情况 A：某个协程在 wait_for(5) 上等，事件循环是空闲的
    → /alive 排在空闲循环里，应该 1.3ms 就返回，不会显示 5002ms

情况 B：事件循环被某个同步操作挡住 5 秒
    → /alive 排在这 5 秒后面，测到 5002ms
```

**测到 5002ms 说明是情况 B —— 要找的不是「哪个 wait_for(5)」，
而是「什么同步操作占了事件循环 5 秒」。**

和今天早上 `emit` 清快照缓存那次同一形态（`snapshot()` 全量计算 → `/alive` 从 1.3ms 涨到 2.5 秒）。

**这一条尚未定位。定位方法（等索引跑完、系统安静后做）：**

1. 每 100ms 发一次 `/alive`，一旦测到 >1s 立刻触发 `py-spy dump`
2. 看主线程卡在哪个函数
3. 候选要从所有 `timeout=5` / `wait_for(..., 5)` 里逐个排除，不能只盯两个

**现状记录：中位 1.3~1.7ms，p99 939ms，只有极少数超过 1 秒。用户未反馈卡顿。**

### 测量环境的教训（2026-11-19 11:24）

做这组对照实验期间，机器上另有一个并行任务在跑 `snap install chromium`
（团队内 t40 的浏览器接入前置验证，由 `/tmp/v1_install.sh` 启动）。
它占用 CPU 与 IO，`no-yield` 组某个窗口掉到 10 job/分、CPU 47.5% 与之时间重合。

**所以上表中 19.0 / 18.4 这组数字带有干扰成分；
安静状态重测是 16 job/分。**

**规则：多 agent 并行时，做任何性能测量前先查机器上有没有别人的任务在跑。**

## 六、yield 对照实验（captain 要求）

| | 有 yield | 无 yield |
|---|---|---|
| done/min 序列 | 20,20,18,14,20,20,18,20,20,20 | 21,19,18,20,20,18,18,10,20,20 |
| 平均 | **19.0** | 18.4 |
| 最低 | 14 | 10 |
| CPU 平均 | 18.5% | 20.8% |
| CPU 峰值 | **36.2%** | 47.5% |
| `/alive` 中位 | 1.7ms | 1.7ms |
| `/alive` 最差峰值 | 5002ms | 5002ms |

**结论：yield 对速率没有负面影响（19.0 vs 18.4），CPU 峰值反而更低（36.2% vs 47.5%），
所以保留。但它不是 `/alive` 5 秒峰值的成因。**

**19.0 job/分是真的，不是采样噪声**（10 分钟 190 个样本，稳定在 18-20）。

## 七、关于扫描顺序

`_unindexed()` 用 `r.occurred_at<?` 作为游标条件，即**从旧往新**扫描。

**captain 提议改成从新往旧，让近期记忆优先可用。**
**没有做，原因：**

1. v1 索引已覆盖 89.7%，近期记录并不缺检索能力
2. 改游标方向要动 `_unindexed` + `scan_enqueue` 的边界条件，风险大于收益
3. 用户要的是「建完」，不是「近期优先」

**如果将来要改，改法是：`ORDER BY r.occurred_at DESC` 配合反向游标，
并重新验证「不重复入队、不遗漏」两个性质。**

---

## 八、结论

**索引是加分项，不是唯一路径。建不完不会让她「查不到东西」——
词法路（75.4%）和 v1 索引（89.7%）一直在兜底。**

**用户要求全量建完，所以按当前速率跑 12.8 小时。
这段期间要盯的是「跑完的路径上会不会出别的事」，不是「能不能快一点」。**
