# 小鱼召回、索引与浏览器：问题收口设计

日期：2026-11-19；状态：设计评审稿，供实现agent制定计划。未修改生产。

输入：`2026-11-19-open-issues.md`、本日云端代码与只读数据库核验。本方案补充现有人格成长及浏览器设计；本期不改变人格底色。

## 1. 核验结论与设计决定

云端HEAD仍为e76b345，工作区另有未跟踪2500和skills/。服务active，NRestarts=0。本次swap已有约88MiB使用，清单“未使用”是过去观测，不能继续作为当前事实。

| 问题 | 决定 |
|---|---|
| P1 语义召回 | 保留；改为先生成排序候选，再对候选精确授权和加载。首版不强制引入ANN |
| P2 ACL | 保持权限语义；请求内复用、批量取规则，不把空表解释成全开放 |
| P3 同步DB | 先为召回建立独立只读连接和有界worker，避免全仓连接池改造 |
| P4 重建 | 限速运行、按资源版本核算覆盖，unknown有界核对；旧索引延后清理 |
| P5/P6 | 优先补模式解析、请求隔离、全轮次观测，再做真实dialogue验收 |
| P7 浏览器 | 沿用云端方案；预配置独立systemd服务，不让模型管理systemd scope |
| P8 契约漂移 | 聚焦本次修改的调用链建立契约测试，不开展全仓逐句注释审计 |

三种路线比较：正式关闭semantic成本最低但损失同义语义检索；直接引入ANN仍不能解决全量ACL和共享连接阻塞；选择候选优先＋权限精查＋专用读通路，后续确有向量计算瓶颈再引入ANN。

保留semantic不等于所有对话都必须等待semantic。近期连续对话依赖历史装配，不能把缺少语义召回等同于“最近聊天记不住”。本方案不取代此前连续输入与历史预算设计。

## 2. 本次发现的两个额外缺陷

`companion.py::_prefetch_recall`显式调用search_async(mode='auto')；`life_recall.py::search`只在mode=None时读取RECALL_MODE_OVERRIDE。故该入口绕过环境变量。search_async本身又在模式规范化前决定是否生成query vector，单改search不够。

非dialogue分支在清空_recall_prefetch/_recall_coverage之前返回。后续_messages仍读取这些实例字段，可能携带上轮召回；这是代码路径风险，尚未以真实泄漏案例复现。

修复要求：
- 统一resolve_mode入口，在query embedding和search之前解析。环境变量作为生产override优先于入口默认；测试需忽略override时用显式诊断选项，不隐式绕过。
- 每轮进入先初始化空结果/coverage/status；最终改成请求局部RecallPacket参数传给_messages，不依赖共享实例字段。
- 取消或超时的旧请求不能修改新请求结果；query_id/source_event_id/权限版本必须匹配。
- text模式不做query embedding、不走向量路线；skipped_non_dialogue不得残留semantic候选。

## 3. 新召回管线

### 3.1 先排序候选，再精确校验

现有allowed()先遍历大量资源并调用access.load，随后search_vectors又逐资源读取向量；结果预算只作用在末端。这是两层N+1和过早加载正文，不能靠调小budget解决。

新管线：规范化请求/绑定scope → 各路线生成排序候选ID → 合并去重 → 对候选做完整权限/来源资格验证 → 只加载通过验证的正文 → 组装预算内结果。

- text：使用已有life_terms按查询词生成相关候选及分数，不先加载全部正文。
- semantic：按agent、model_key、chunker_version及当前source_version读取有效向量；首版使用批量向量快照做精确相似度排序。返回分数与ID，不加载候选正文、不绕过权限。
- related：从指定人物/实体及边关系得到候选；不要每轮扫描所有资源关系。
- exact_refs：单独解析并授权，不能因为语义得分低被裁掉。
- 明确的时间/人物筛选可以前推；未要求“最近”时不得强加时间窗，旧记忆要有机会命中。
- 维持既有多路线融合语义；以旧实现为离线oracle校验结果差异，不假设改排序后行为相同。

候选不是“随便取最近N条”。按查询相关度分页取，例如先64条，授权不足时继续128/256；这只是初始可调批大小。达到请求期限还不够时返回partial及截断原因，不伪称完整无匹配。优先实现确定性全量排序ID，再按需授权；ANN是后续替换候选生成器，不能改变权限检查。

对于多个路线，逐步扩展至各路线所需的已授权候选数量，或其后续分数已不足以进入结果；若融合算法无法证明完备就标partial。不能用未授权候选占满top-K后直接返回空。

### 3.2 向量缓存和存储

不新建一份权威向量库。以现有SQLite为真相，内存使用紧凑数值数组/矩阵及ID、版本映射，不能用大量Python float对象膨胀内存。按更新水位增量刷新；删除/失效即时检查，缓存落后时报告coverage。

先测批量读取、计算与授权各耗时及峰值内存。若紧凑缓存仍超过召回资源预算或计算占据主要时延，再评估ANN；不为“先进”直接加入新数据库。不得把不同model_key或chunker版本混为一个向量空间。

### 3.3 权限正确性

当前life_acl=0行，但_allowed仍包含：全局internal_use deny、用途/受众deny、internal、diagnostic、同scope、同人群事件及显式allow/ancestry规则。保留其全部顺序和含义。

请求内一次读取固定epochs与相关规则；若一致性快照中ACL为空，仅令effects为空并省掉SQL，不return True。不要求为了性能凭空补写allow行。祖先共享时复用原有请求内缓存，并保留学习撤销、过期、删除与会话绑定校验。

读取使用一致性快照；结果送入模型前再次核对授权/删除/遗忘版本。期间发生变化，重新授权最终集合或丢弃本次结果。首次实现必须审计所有授权变更入口，确保版本递增；无法证明时直接精查最终结果，不用不可靠版本缓存。

内部候选可跨scope计算排名，但候选正文、ID、分数和数量不得向未授权受众暴露。首版禁止跨请求缓存最终授权结论。空ACL、deny新增/删除、到期、祖先拒绝、diagnostic及跨scope均需差分测试。

## 4. SQLite与事件循环

Repository现在是单连接+threading.RLock，不能只包一层to_thread后宣称已隔离。等待锁仍可能拖住其他同步路径；wait_for超时也不保证工作线程停止。

建立RecallReadSession：在专用worker中创建只读SQLite连接，query_only开启；确认现有数据库WAL模式后使用短读事务。只读session及其catalog/access依赖必须绑定该连接，不能中途回到主Repository共享锁。不在跨线程传递sqlite Row、活动游标或事务。

首版一个专用召回worker，最多一个运行请求＋一个最新待处理请求；新查询可替换尚未运行的旧查询。运行任务合作取消：CPU循环检查deadline/cancel，SQL使用进度回调/interrupt；结束回滚读事务并清理回调。模型等待超时后禁止后台无限继续占用连接。

query embedding异步执行并受同一总deadline约束，不在SQL读事务内等待网络。主线程只接收不可变候选包和短校验结果。

search目前会为分页写meta快照；专用读通路不能照搬该写入。对话预取首版不生成持久分页游标；需要用户分页的显式检索保留单独受控写路径，将已算好的短快照交主写者事务保存，不能把长检索放在写锁中。

优先修召回路径，不一次性把所有Repository调用换连接池。记录事件循环延迟、主锁等待和/alive时延，再定位其余同步热点。/alive仅检查进程存活，不构造snapshot或执行DB扫描；响应快不代表召回健康。

## 5. 时限、降级和可观测

先保留text override作为临时可逆策略；它必须在所有调用路径真实生效。预算建议：交互预取总等待800ms；这是目标而非保证。慢请求返回已有text候选及semantic_timeout/deadline状态，不清空已经得到的结果。

调度必须支持这一降级：auto请求启动异步query embedding的同时，专用读worker先计算并授权text结果，形成请求局部的可用检查点；embedding及时返回后，再由同一worker执行向量候选和融合。不得沿用“先等embedding，再开始全部search”的串行入口。截止时仅返回已授权检查点；若text也未完成，明确记录deadline且本轮无召回，不承诺一定有词法结果。对外返回之前完成最终权限校验，校验未能在期限内完成则丢弃结果。

不自动把超时结果注入下一轮。只有同一query、同一意图和权限版本匹配才能复用，否则用户换话题后会拿到无关结果。

复用companion_context_loads的扩展JSON字段（实施前核对消费者兼容），每次认知记录一个recall对象，无须再建一张每步骤流水表。包括：request/source/purpose、requested/effective_mode、skip_reason、每路线attempted/status/count、candidate/authorized/returned数量、query_embed/candidate/auth/load/total_ms、coverage、timeout/cancel、model/chunker/epoch。日志不记原文查询和私聊正文。

分清：semantic成功运行、找到匹配、实际装入上下文是三个计数；text跳过不算失败。计算分母按合资格dialogue请求，不能用“日志0条”证明成功。以小时/日聚合观察，明细沿用当前诊断保留策略。

## 6. 索引重建与旧数据

本次核验：memory_index done20615、pending9827、running5、unknown4；unknown都是embedding_outcome_unknown、attempts=2。v1 ready27630、v2 ready52808。同一资源可有多个chunk，多行不等于多份记忆；done总数也不等于当前版本覆盖率。

重建采用query embedding优先、后台build有界并发。先保守以一个build在途，根据实际推理吞吐增加；running5要核对租约，不直接认定五个有效并发。浏览器任务期间暂停领取新的低优先级build，已在途允许完成；这不会自动释放常驻embedding模型内存，不能虚报内存收益。

unknown先核对已有结果及请求幂等键，区分服务超时、响应不匹配、预算与进程失败；指数退避且最大尝试数明确，超过后paused并报原因。禁止把unknown批量改done或无限重跑。剩余9827任务不保证全部成功。

按当前有效资源版本计算覆盖：可索引资源数、已覆盖资源、缺失chunk/版本、不可索引原因。用最近30分钟成功吞吐估算ETA及波动区间；清单9895/16约10.3小时，不应同时写7~8小时。

v1暂时保留用于回滚，不参与v2查询混排。仅在对应资源当前版本已有完整v2覆盖、读路径切换验证、恢复点可用后分批清理；复用现有cleanup实现并验证条件。不得为释放空间先删除原始事件或记忆。

## 7. 浏览器收口决策

继续已有云端设计A→B→C，环境V1-V4不重复安装。清单中的Chrome/Node/AppArmor/635MB峰值本轮未全部复测，交付时引用原实验命令与独立cgroup证据，不把报告数字当新实测。

选择安装时预配置的独立`companion-browser.service`（单实例），User=companion，独立cgroup、进程组收尾、资源上限；服务可按需启动或轻量Node常驻、Chrome任务结束退出。优先轻量Node常驻方案，避免运行时需要systemd管理权限。适配器不能任意执行systemd-run或自行改变限额。

专用Unix socket同用户访问（或已有本机stdio管理若能满足独立cgroup）；默认选Unix socket，路径位于受限运行目录，peer身份验证，不开公网端口。结构化请求、action_id幂等、取消和未决查询沿用浏览器设计。

任务开始=首个browser动作被执行端接收并获得project绑定session租约；任务结束=完成/取消/失败，或空闲期限到且无在途操作。模型思考期间保留浏览器状态；每次click不重启。释放租约不自动重执行unknown；新任务不得拿到旧任务错误页面引用。

GUIDES建议：普通公开正文/搜索优先web；需要动态加载、页面交互或已验证procedure时使用browser。401/403和登录要求先解释，不把换浏览器当成保证绕过。常见会话要完成“打开→操作→提取→核验→关闭”整项链路。

任务串行、单浏览器；加入浏览器＋索引同时运行时的压力验收。swap当前已用约88MiB，监测换页与交互延迟；不因有swap就放开并发，也不因出现少量swap就判故障。

## 8. 实施顺序与验收

1. **小修与观测**：修模式override、请求状态隔离、每轮recall记录。测试text不调用embedding、非dialogue结果为空、超时旧请求不能污染新轮。
2. **召回管线**：先ID排序再权限精查，独立只读session、有界worker与取消。旧实现作为隔离数据副本中的正确性oracle，不能在线反复全扫制造压力。
3. **真实dialogue验证**：经实际入口发送获授权测试问题，等待完整气泡，核对source至RecallPacket至实际上下文链；模拟和真实测试分开，不声称无对话期间guard已验证。
4. **索引调度/恢复**：公平调度、unknown分类、有界重试、当前版本覆盖；最后才清理v1。
5. **浏览器A/B/C**：按既有设计交付，并与召回/索引混合压测；不要求等一万条索引全建完才能开始开发。

建议首轮目标（待实测调整，不是当前表现）：典型私聊召回p95≤800ms、正常/alive p95≤100ms；混合负载无多秒事件循环阻塞、无无界排队、无OOM。报告样本数、p50/p95/max与冷/热缓存，不只报均值。

质量集至少覆盖：旧记忆同义问法、最近消息、精确引用、无结果、未索引资源、同人跨会话、不同人不可见、撤销/删除/过期、deny变化、分页失效。权限测试不得回归；候选裁剪带来的命中损失必须显式报告。统计semantic实际参与结果的比例，而非仅仅“不超时”。

P8按同一规则处理：每个新增或修改的对外承诺对应一项验收；特别是“取消会停止”“text不查语义”“ready表示可用”“unknown会恢复”。不靠检索must/should做全仓形式审计。修复提交同步更正过时注释与工具说明。
